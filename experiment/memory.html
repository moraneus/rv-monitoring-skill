What it is

A browser Memory-pairs game

A 4×4 grid; flip two cards, matches stay up. Three entity kinds with disciplined keys: cards on a composite key, attempts on their own key, games on game_id.

Rules 1 and 3 use history-stamped fields with self-contained nevers, precisely so the completion terminal cannot blind them.

event model  · game.start, card.flip, match.found, attempt.resolved, terminal game.completed; stamped fields already_matched and after_completion.

The monitored rules

What the user asked the monitor to enforce

Verbatim from the committed monitoring/policies/. These are the human's own words; the engine owns the verdict.

Feature: attempts resolve promptly Scenario: an attempt resolves within 3 seconds When the second card of an attempt is flipped Then the attempt resolves within "3" seconds

Feature: a finished game stays finished Scenario: nothing happens after the game is over Then a card is flipped after the game is over never happens

The sabotage

The bugs planted in the app code

Bug 1 - the resolve emit is mis-scoped

  def _close_attempt(self, attempt_id):
      if len(self.matched) == BOARD_SIZE:
          self._complete()
-     self._resolve(attempt_id, "matched")      # every match resolves
+         self._resolve(attempt_id, "matched")  # nested: only the LAST does

A one-level indentation slip nests the resolve emit inside the board-complete branch, so only the final matched pair ever emits attempt.resolved. Every intermediate match arms the 3-second deadline (on the second flip + match) and then lets it lapse. The monitor fires rule 2 live on nearly every honest attempt.

Policy in play: 02 - attempt resolves within 3s  ·  Trigger: match any pair that is not the last  ·  Class: normal-use

Bug 2 - flip-back is slower than the deadline

- FLIPBACK_DELAY = 1.1   # under the 3s deadline
+ FLIPBACK_DELAY = 3.5   # over it

A mismatch now flips its cards back after 3.5 seconds - past the 3-second resolution deadline - so every real mismatch also violates rule 2. A second, independent way the same rule is tripped by honest play.

Policy in play: 02 - attempt resolves within 3s  ·  Trigger: any mismatched pair  ·  Class: normal-use / timing

Detection

How the failure surfaced

The same defect through the framework's three independent channels, plus what the blind user actually noticed.

Channel A - live runtimecatch

Rule 2 fired violated on nearly every honest attempt (22 of 23 in one game) - the deadline lapsing on unresolved matches and slow flip-backs. Rules 1 and 3 correctly stayed satisfied.

Channel B - replay gatered · exit 1

replay_check.py failed decisively - 23 violations against the pinned 4.

Channel C - stability contractrisk · exit 1

The stability contract flagged _close_attempt and _resolve as risking rule 2.

The blind userfound 2 / 2

Traced both causes - the mis-scoped resolve and the slow flip-back - and noted a downstream UI symptom (the board locking on "resolving…") that the monitor cannot see but which follows from the same root cause.

A deadline rule earning its keep. An indentation slip that silently breaks resolution is exactly the kind of bug a within monitor is built to catch by absence - and it fired, live, on ordinary play, with the stability contract naming the changed function.
