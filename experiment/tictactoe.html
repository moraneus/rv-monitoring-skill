What it is

A browser tic-tac-toe for two players

Two players at one keyboard click squares; the game emits events and a live dashboard watches three laws. This build is where the project discovered that triggered forms arm once per entity - so alternation is checked via an app-stamped prev_player field on a self-contained never.

The won/draw finish is not the terminal; a separate game.over event (including "abandoned") is, so law 3 can actually fire.

event model  · game.status (started/move/won/drawn, moves carry prev_player + after_finish) and a terminal game.over - keyed by game_id.

The monitored rules

What the user asked the monitor to enforce

Verbatim from the committed monitoring/policies/. These are the human's own words; the engine owns the verdict.

Feature: turn alternation Scenario: players must strictly alternate turns Then the same player moves twice in a row never happens
Feature: play stops once the game is decided Scenario: no move after the game is won or drawn Then a move is played after the game is decided never happens
Feature: every game reaches an end Scenario: every game that starts must eventually be decided Then a game is decided has happened

The sabotage

The bugs planted in the app code

Bug 1 - the turn never toggles

  else:
-     self._current = "O" if player == "X" else "X"   # alternate
+     self._current = "X" if player == "X" else "O"   # never changes

Both arms of the ternary resolve to the mover's own mark, so after X moves the current player stays X - every move comes out X and the board fills X, X, X. O never appears; draws are impossible. Because prev_player is still stamped honestly, the repeat is a genuine, visible violation and the alternation law fires live on every game.

Policy in play: 01 - strict alternation  ·  Trigger: start a game, click any three empty cells  ·  Class: normal-use

Bug 2 - a corrupted winning line

- WIN_LINES = [..., (0, 4, 8), ...]   # the main diagonal
+ WIN_LINES = [..., (0, 4, 7), ...]   # corrupted

One of the eight winning lines is wrong (0,4,7 is not a line). Win-detection is subtly broken - but no policy asserts on which cells constitute a win, and in an all-X game that diagonal is never legitimately reached, so the user did not surface it.

Policy in play: none - win-detection is unasserted  ·  Trigger: a game reaching the main diagonal  ·  Class: subtle · slip-through

Detection

How the failure surfaced

The same defect through the framework's three independent channels, plus what the blind user actually noticed.

Channel A - live runtimethe hero

The alternation law fired violated at runtime on every multi-move game, with a clean replayed explanation; law 3 correctly flagged an abandoned game; law 2 correctly stayed green (the honest path refuses post-decision moves).

Channel B - replay gatered · exit 1

replay_check.py failed. A rough edge: the demo and gate crash with an uncaught GameOver on their "clean draw" flow - the all-X play wins early, so a later scripted move hits a decided board - a loud (if indirect) failure.

Channel C - stability contractrisk · exit 1

catalog diff failed, flagging GameService.play as behavior-risk against all three policies.

The blind userfound 1 / 2

Caught the alternation bug three ways and called the monitor the hero. The corrupted win-line was unreachable in all-X play and unasserted by any policy - not surfaced.

The clearest pure-runtime catch in the corpus. A live policy verdict, not a stability flag or a gate exit code, is what told the user the game was broken - on a bug that made the game fundamentally unplayable. The unfound second bug is a property no rule was written to watch.
