The implanted bugs

policy-targeted app/booking_service.py

Off-by-one in the class-capacity check inside reserve(): the guard was changed from `len(seats) > CLASS_CAPACITY` to `len(seats) >= CLASS_CAPACITY`. Exactly CLASS_CAPACITY (12) seats is full but NOT over capacity, yet the app now emits the booking.cap_exceeded marker on the 12th reservation as well as the 13th.

Expected effect: The over-capacity marker fires one reservation too early. In the pinned replay traffic (13 members reserved into C-FULL) it now trips on B-C12 (seat 12, legal) in addition to B-C13 (seat 13, the real breach), so policy 07 ('a booking never pushes its class over capacity') reports an extra violation for B-C12 that the gate does not expect.

blind-spot probe app/booking_service.py

Wrong status string in mark_no_show(): emits status "no-show" (hyphen) instead of the canonical "no_show" (underscore) that END_STATES and the catalog use. A plausible slip when aligning with a display/API label.

Expected effect: A no-show booking no longer matches the 'a booking reaches an end state' predicate, so policy 06 ('every booking eventually reaches an end state') can never be satisfied for no-show bookings and the value silently stops matching any policy binding. Because policy 06 is an unbounded eventuality that only ever reports 'pending' (never 'violated') in the bounded replay, the gate's pinned violation set is unchanged and the fault slips through unseen.

Blind user (monitor only)

An agent that never saw the ground truth, working only from the monitor:

  • Capacity off-by-one: BookingService.reserve fires the booking.cap_exceeded marker with `if len(seats) >= CLASS_CAPACITY` (CLASS_CAPACITY=12). Exactly 12 seats is AT capacity, not over it, so the legal 12th booking (B-C12) is falsely flagged (cap_exceeded with seat_count=12). Should be `> CLASS_CAPACITY` / only the 13th seat. The replay gate caught this as an UNEXPECTED 7th violation (policy 'a booking never pushes its class over capacity', entity B-C12) turning the gate red (exit 1); the catalog stability diff independently flagged reserve on the cap_exceeded emit path as a behavior-risk. via both
  • Status value naming drift: mark_no_show emits status 'no-show' (hyphen) but the end-state matcher END_STATES in monitoring/steps.py and the committed catalog.json both use 'no_show' (underscore). A no-show booking therefore never matches 'a booking reaches an end state', so policy 06 (every booking eventually reaches an end state) silently leaves that booking pending instead of satisfied (tally shows satisfied=5 = 3 attended + 2 cancelled; the one no-show booking is missing). This is a silent-telemetry-gap: the replay gate cannot go red on a 'has happened' eventuality in bounded no-terminal replay, but the catalog stability diff surfaced it, flagging mark_no_show as a changed function on the booking.status emit slice with 'every booking eventually reaches an end state' as a policy at risk. via both
