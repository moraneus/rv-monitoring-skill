Do the monitors catch real bugs?

A controlled experiment: implant realistic bugs in ten monitored demo apps, then measure whether the runtime monitor and its two-sided stability contract catch them, and whether a user relying only on the monitor would notice.

How it was run

Each of the ten demos ships an app, a runtime monitor (Gherkin policies compiled by behave-rv), and a two-sided stability contract. The steps, in order:

  1. Freeze the baseline. All ten demos pass both gates clean; the monitoring layer is hash-frozen.
  2. Sabotage. One agent per demo implants two realistic bugs, editing only app/ code. By design one bug targets a monitored behavior and the other probes a blind spot. Ground truth is recorded separately.
  3. Measure three channels. The stability contract (catalog diff --fail-on-app-risk), the runtime gate (replay_check.py, which drives the real app code), and a blind agent that never sees the ground truth and must find the bug through the monitor alone.

The monitoring layer was verified byte-identical before and after sabotage on all ten demos, so every detection is attributable to the implanted app bug, not to a changed policy.

What it shows

The stability contract is the reliable catch-all. It flagged the code change in all ten demos, including every blind-spot bug, because it detects behavioral change on an emit path whether or not a policy happens to cover it.

The runtime monitor catches what its policies cover. The ten policy-targeted bugs surfaced as live violations; the ten blind-spot probes (an unbound field, an unbounded eventuality that only ever pends, a wrong value that still matches, an uncovered code path) mostly slipped it. That gap is real and is exactly why the stability contract exists alongside it.

A user relying on the monitor noticed in every demo. In all ten, the monitor surfaced a problem (a red gate, a live violation with a rendered explanation, or a stability flag) and the blind agent traced it to the bug, confirming in code afterward.
