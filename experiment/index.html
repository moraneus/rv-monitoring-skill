Does an embedded runtime monitor actually find real bugs?

Ten small applications, each built to ship with its own live behave-rv monitor. A saboteur planted 19 realistic bugs in their code. Ten people, told nothing, used each app and watched its monitor. This is what happened.

The premise

Software that is born monitorable

behave-rv turns human-readable Gherkin rules into deterministic per-entity monitors that watch a running program's event stream and emit a verdict - satisfied, violated, or pending - for every rule, for every thing it tracks, in real time. The rules are the human's; the verdict is the engine's; no model sits in the runtime path. An agent skill (rv-monitoring-skill) lets a coding agent instrument an application as it writes it, so the software that leaves development already carries a runtime monitor inside it.

The open question a reasonable skeptic asks: fine, but if the code has a genuine bug, does the monitor actually catch it - or does it just decorate a green dashboard? This experiment was built to answer that with numbers instead of assertions.

Background

What the monitor is watching

Each application emits an Event(type, event_time, bindings, payload) at every state transition. A policy is one Gherkin scenario compiled to a monitor: a never prohibition, a before/previously precedence, a within deadline that fires on the wall clock when nothing arrives, an always holds invariant, or a scoped/since window. Every emit site and every step predicate is fingerprinted into a committed two-sided contract (catalog.json), so a code change that could move what the monitor sees is flagged at build time. There are, in effect, three ways the framework can raise a hand.

Channel A · live

Runtime verdict

A policy card flips to violated as the buggy behaviour actually happens, with the authored scenario replayed and the failing step marked.

Channel B · replay

Pinned gate

A committed replay_check.py runs scripted traffic against pinned verdict counts and exits non-zero when the counts move - a CI merge gate.

Channel C · stability

Contract diff

catalog diff --fail-on-app-risk compares current code to the committed contract and flags behavior-risk on any changed emit-path function - even before a single event flows.

Method

The experiment, in three blind stages

Build. Ten demos were built from scratch by dedicated agents driving the rv skill against behave-rv 0.3.1 - five services (lending, parcels, bookings, devices, payments) and five browser games (snake, blackjack, minesweeper, tic-tac-toe, memory), each with a live dashboard. All ten passed their gates green before anything was touched.

Sabotage. One saboteur agent - using no monitoring knowledge - planted one or two realistic bugs into each demo's application code only, and recorded each one privately with a prediction of whether the monitor would catch it. Every monitoring/ tree was verified byte-for-byte unchanged; every demo still imported and ran. The bugs were deliberately varied: some clearly policy-violating, some subtle edge cases, some outside what any policy asserts.

Play. Ten "user" agents, each blind to the bugs and forbidden from reading the saboteur's notes, exercised their demo hard through its real interface - the game APIs over HTTP, the service classes directly - for a long session of normal play and edge cases, watched the RV dashboard, and wrote an honest report of anything wrong. Only afterward were the three channels scored against the recorded ground truth.

Integrity. Across the whole run, exactly ten application files changed and zero monitoring files did (confirmed by hash before and after). So every stability-strip change a user saw was real, and the comparison is clean.

Coverage by channel

No single alarm is enough - together they never missed a demo

The most important result is not a single number but a shape. The three channels fail differently, and their union is what makes the framework trustworthy.

Channel A · live

The loudest, the most foolable

Caught the wrong behaviour of most bugs - sometimes spectacularly (blackjack paying losers, tic-tac-toe's all-X games). But a buggy emitter can fool it: lending fired the wrong policy, parcels' rule went dormant, bookings raised false alarms on healthy data.

~13 / 19 behaviour caught

Channel B · replay

Deterministic, but only as good as its traffic

Went red in seven of ten demos. It passed in three (lending, snake, minesweeper) - because the pinned scripted traffic didn't drive the buggy branch, or a misdirected fault preserved the count. A real methodology lesson: seeds must exercise the real engine, not bypass it.

7 / 10 demos red

Channel C · stability

The quiet backstop that never missed

Every bug touched an emit-path function or constant, so the two-sided contract flagged behavior-risk on all ten demos - before a single event flowed. It names the changed function, not the specific defect: a coarse but perfectly reliable "the watched code moved."

Interpretation

What the experiment actually shows

  1. The embedded RV finds real app-logic bugs.

    Every one of the ten demos had its injected defect surfaced by at least one automated channel, and the blind users found 17 of 19 with the monitor as their primary lever - not a decorated green dashboard.

  2. The live verdict cards are the loudest signal and the most foolable.

    When the bug is in the logic, the monitor catches it beautifully. When the bug is in the emitter - a wrong status string, a swapped field - the cards can lie: a dormant policy, a misdirected verdict, or a false alarm on healthy data. Reading verdicts alone is not enough.

  3. The stability contract is the quiet backstop.

    It fired on all ten because every bug perturbed an emit-path function. It cannot diagnose the defect, but it never let a change to the watched code pass unremarked - exactly the "specifications don't rot silently" promise the framework was built around.

  4. The two bugs that slipped were the ones the design predicts.

    A device terminal-timestamp offset and a corrupted tic-tac-toe win-line: both subtle, both unasserted by any policy, one unreachable in the broken game's play. The saboteur predicted both as slip-throughs before anyone played.

  5. A monitor watches the event, not the world.

    The coverage gaps map precisely to documented limits: it sees only the fields a policy binds (lending's swap), the event a policy names rather than the state (snake never grows yet emits "grew"), and the properties a policy asserts (blackjack's untracked push payout). Those bugs are the user's to catch - and every buggy demo's own README and pinned gate became false, which the gates flagged.

The honest one-line answer. Yes - the embedded monitor finds real bugs, and its blind spots are knowable in advance from what its policies bind. Its verdict cards are the alarm; its pinned gate is the merge guard; its stability contract is the tripwire. You want all three, and you want them because they fail in different places.

Caveats

Where this evidence stops

This is a designed experiment, not a field trial. The apps are small; the bugs were planted by one saboteur with knowledge of the fragment; the "users" are agents playing a human role. The numbers show that RV can catch real bugs and where its channels fail - they do not prove a catch rate on an arbitrary production codebase, and the coverage gaps (event-not-state, unbound-fields, unasserted-properties) are inherent to any specification-based monitor: it enforces what you wrote, no more. The reliable, load-bearing finding is the shape, not a headline percentage: three complementary channels, none sufficient alone, whose union raised a hand on all ten demos.
