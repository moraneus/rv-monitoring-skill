What it is

A dispute-aware payment tracker

A PaymentService: authorize → capture → close, with an optional dispute → investigate → refund → close path. The rules were resolved through a conflict (the user's first wording was jointly unsatisfiable and the gate went red by design until they chose).

Rule 1 is scoped on a frozen marker; rule 2 binds to a distinct disputed-close marker so plain closes stay free.

event model  · payment.status keyed by payment_id; a payment.dispute_closed marker; a terminal payment.closed; a frozen-rejection event.

The monitored rules

What the user asked the monitor to enforce

Verbatim from the committed monitoring/policies/. These are the human's own words; the engine owns the verdict.

The sabotage

The bugs planted in the app code

Bug 1 - refund emits the wrong status payload

  self._status[id] = "refunded"                # internal state is CORRECT
- self._emit(Event(..., {"status": "refunded"}))  # but the event...
+ self._emit(Event(..., {"status": "refund"}))    # ...says "refund"

No refunded status event is ever observed. The refund-before-close rule can no longer be satisfied, so it fires violated on a correctly-refunded payment exactly as it does on a truly unrefunded one. The rule collapses into a constant alarm that no longer discriminates good from bad - arguably worse than silence.

Policy in play: 02 - close requires prior refund  ·  Trigger: authorize → capture → dispute → investigate → refund → close  ·  Class: normal-use

Bug 2 - frozen rejection carries the wrong reason

- reason = "frozen"
+ reason = "declined"

A frozen-action rejection now reports declined. The step phrasing that binds reason="frozen" becomes dead - that check can never match again.

Policy in play: the frozen-rejection phrasing goes dead  ·  Trigger: new charge attempt on a frozen payment  ·  Class: subtle · slip-through predicted

Detection

How the failure surfaced

The same defect through the framework's three independent channels, plus what the blind user actually noticed.

Channel A - live runtimecatch

Policy 02 fired violated on payments that were correctly refunded (P-2002) - the constant-alarm signature. Loud, though it misdescribes a correct resolution as "closed without refund".

Channel B - replay gatered · exit 1

replay_check.py failed - 4 violations against the pinned 3 - and the emit-side contract named refund#1 and policy 02 precisely.

Channel C - stability contractrisk · exit 1

The stability contract flagged the refund emit slice as behavior-risk, and separately the frozen-reason change.

The blind userfound 2 / 2

Caught the refund bug (noting the rule no longer discriminates) and the secondary frozen-reason bug - the latter spotted as a now-dead step phrasing plus a risk flag, beating the saboteur's slip-through prediction.

A safety rule that always fires is a rule you stop believing. The monitor was loud, but the failure mode is a false-positive flood, not a miss - and the observant user plus the stability channel caught the subtler payload bug the design expected to slip.
