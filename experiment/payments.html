The implanted bugs

policy-targeted app/service.py

refund() emits the status transition with the wrong status string "refund" instead of "refunded". A copy/typo-style slip in the emitted enum value.

Expected effect: Policy 02 (a disputed payment must be refunded before it closes) can no longer see the 'refunded' status. A correctly-handled disputed payment that is investigated, refunded, then closed (e.g. P-2002) now fails the 'a payment is "refunded" before' precedence check and is reported as a rule-2 VIOLATION even though it was refunded. The trigger 'a payment is disputed or closed' (resolved set) is unaffected; only the refunded-precedence rule breaks.

blind-spot probe app/service.py

attempt_customer_action() checks self._status.get(payment_id) == "frozen" instead of payment_id in self._frozen. Frozen state is tracked in the _frozen set and never appears as a status value, so this guard condition is always False.

Expected effect: The frozen guard is silently disabled: a customer action on a frozen (disputed) payment is now allowed and no payment.rejected 'frozen' event is emitted; the method returns True instead of False. This is a genuine safety-guard failure, but no policy asserts on the payment.rejected event (the payment.rejected.frozen trigger is defined but unused), and the method emits no charge status event, so rule 1 (no authorized/captured after freeze) does not fire either. Intended to probe the monitor's blind spot.

Blind user (monitor only)

An agent that never saw the ground truth, working only from the monitor:

  • refund() emits the event payload {"status": "refund"} while setting internal state to "refunded" (app/service.py:77-80). Every other place uses the enum value "refunded" and policy 2 asserts `a payment is "refunded" before`. Because the live status string is "refund", the healthy disputed->refunded->closed flow for pA violates rule 2, and control fault seed pW also violates, giving 4 fault violations instead of the expected 3. replay_check.py exits 1 (FAIL); the stability diff flags refund#1 as behavior-risk with those policies at risk. via both
  • The frozen guard in attempt_customer_action checks `self._status.get(payment_id) == "frozen"` (app/service.py:106), but _status is never set to "frozen" (statuses are authorized/captured/disputed/investigated/refunded/closed); frozen-ness lives in the separate self._frozen set. So the guard is always False: an action on a frozen/disputed payment is never refused and the payment.rejected ("frozen") event is never emitted, contradicting the README/docstring. Correct check is `payment_id in self._frozen`. The stability diff flags attempt_customer_action#1 as behavior-risk (new unresolved call self._status.get). No active policy observes payment.rejected, so the runtime verdict gate does not catch it; confirmed by reading the code. via both
