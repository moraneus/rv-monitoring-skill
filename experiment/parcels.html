The implanted bugs

policy-targeted app/parcel_service.py

hub_scan emits status "arrived" (and sets parcel.status = "arrived") instead of "scanned" - a status-vocabulary rename applied in the code but not reflected in the monitored 'scanned' value. Every hub scan now announces 'arrived' rather than 'scanned'.

Expected effect: Policy 01 (hub scan before dispatch) requires a parcel to be 'scanned' before 'out_for_delivery'. Since the scan event no longer carries status='scanned', the precedence check sees no prior scan, so even correctly-scanned healthy parcels (P-1001, P-1004, P-1005, P-1003) falsely violate rule 1 at dispatch. Classic silent-rename / status-string gap.

blind-spot probe app/parcel_service.py

route_to emits the reroute event with hub=parcel.destination instead of the actual routing hub (parcel.hub / the hub argument). The 'hub' payload field on a rerouted event is wrong.

Expected effect: The parcel is still routed and status='rerouted' is emitted correctly, so rule 2 (no reroute after delivery) still triggers. But the 'hub' field is wrong. No policy references the 'hub' payload field, so this data-corruption bug is a monitor blind spot.

Blind user (monitor only)

An agent that never saw the ground truth, working only from the monitor:

  • hub_scan() emits status="arrived" instead of "scanned". Policy 01 (hub scan before dispatch) requires a parcel to be "scanned" before going "out_for_delivery", but the app now emits "arrived" for the hub scan, so the precedence never matches. The recorded trace (live_session.jsonl) still holds 4 "scanned" events and the catalog/STEPS.md list "scanned" as a real value, confirming the value was renamed from scanned->arrived. Effect: replay_check.py exits 1 with 7 violations vs the expected 3 - four spurious rule-1 precedence violations on parcels H1, H2, FB, FC that all actually WERE hub-scanned. The catalog diff also flags hub_scan#1 as behavior-risk against this policy. via both
  • route_to() emits the wrong hub value: it sets parcel.hub = hub but emits payload {"status": "rerouted", "hub": parcel.destination}, so the emitted hub field carries the destination address instead of the hub the parcel was routed to (visible in the FB reroute explanation as hub='77 Birch Ln'). The catalog stability diff flags route_to#1 as an app behavior-risk. No committed policy reads the hub field on a rerouted event, so it does not change any verdict, but it is a surfaced app-behavior risk and a genuine payload inconsistency. via both
