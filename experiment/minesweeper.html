What it is

A browser Minesweeper with per-cell monitoring

8×8, 10 mines, click to reveal, right-click to flag. Cells are monitored under a composite key so "revealed at most once" is checked per square, per game.

The win-only terminal is a deliberate cleverness: because a boom (loss) and the terminal (win) are mutually exclusive, rule 1 has no terminal blind spot at all.

event model  · mine.boom, board.reveal (game-keyed) and cell.reveal/cell.seen (composite key), flag.set (carries flag+mine counts), terminal game.done on win only.

The monitored rules

What the user asked the monitor to enforce

Verbatim from the committed monitoring/policies/. These are the human's own words; the engine owns the verdict.

Feature: a detonated board is frozen Scenario: no cell is revealed after a mine explodes Given a mine explodes Then a cell is revealed on the board never happens
Feature: each square is revealed at most once Scenario: a cell is never revealed twice Given that cell was already revealed Then a cell is revealed never happens
Feature: the flag budget is never exceeded Scenario: planted flags never outnumber the mines Then the planted flags outnumber the mines never happens

The sabotage

The bugs planted in the app code

Bug 1 - a lost board is not frozen

  def reveal(self, cell):
-     if self.status != "playing": return   # frozen after win OR loss
+     if self.status == "won":     return   # frozen only on a win

After you hit a mine (status → lost), the freeze guard no longer triggers, so you can keep revealing cells. The monitor catches it live: rule 1 (no reveal after a mine explodes) fires as the post-boom reveals happen.

Policy in play: 01 - no reveal after explosion  ·  Trigger: reveal a mine, then click any other square  ·  Class: normal-use

Bug 2 - flag budget off-by-one

  def toggle_flag(self, cell):
-     if len(self.flagged) >= self.mines: return  # budget = mines
+     if len(self.flagged) >  self.mines: return  # allows one extra

You can now plant mines + 1 flags. The monitor catches it live: rule 3 (flags never outnumber the mines) fires on the 11th flag of a 10-mine board.

Policy in play: 03 - flags within budget  ·  Trigger: flag 10 squares, then flag one more  ·  Class: subtle · edge

Detection

How the failure surfaced

The same defect through the framework's three independent channels, plus what the blind user actually noticed.

Channel A - live runtimecatch ×2

Both bugs produced live violations: rule 1 on the reveal-after-boom, rule 3 on the over-budget flag, each with a rendered counterexample. Rule 2 (double-reveal) correctly stayed satisfied.

Channel B - replay gatepass · exit 0

The pinned gate passed (92 verdicts / 3 violations) - its scripted corruptions still fire, but they don't exercise the two buggy engine branches, so the count held. The live play, not the gate, is what caught these.

Channel C - stability contractrisk · exit 1

catalog diff --fail-on-app-risk failed from startup, naming the changed emit-path functions (reveal, _flood_reveal, toggle_flag) and the exact at-risk policies.

The blind userfound 2 / 2 (+1)

Caught both bugs through live play, and additionally found an out-of-coverage bug by eye - reveal() does no bounds-checking, so out-of-range HTTP reveals create phantom cells - correctly noting the shipped policies don't watch it.

The strongest runtime showing. Two real game bugs, both caught by live policy verdicts as the user played - the clearest demonstration that an embedded monitor finds real logic bugs, not just contract drift. The one bug outside the rules (bounds-checking) is precisely the kind only a human catches.
