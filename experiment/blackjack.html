What it is

A browser Blackjack table

Player vs dealer, one deck, hit / stand / new-hand. Each dealt hand is one monitored entity. A hand closes after payout (the terminal).

Rules 1 and 2 are scoped to the player; dealer draws after a stand are the game, not a violation.

event model  · hand.dealt, hand.stood, hand.busted, hand.settled (outcome), hand.payout, terminal hand.closed - keyed by hand_id.

The monitored rules

What the user asked the monitor to enforce

Verbatim from the committed monitoring/policies/. These are the human's own words; the engine owns the verdict.

Feature: losing hands are not paid Scenario: a hand settled as a loss is never paid out Given the hand is settled as "lose" Then a payout is made for the hand never happens
Feature: a busted hand never wins Scenario: a hand that busts is never settled as a win Given the hand busts Then the hand is settled as "win" never happens
Feature: a payout only follows settlement Scenario: a payout is made only after the hand is settled When a payout is made for the hand Then the hand is settled before
Feature: every hand settles in time Scenario: a dealt hand reaches settlement within 30 seconds When the hand is dealt a card Then the hand is settled within "30" seconds

The sabotage

The bugs planted in the app code

Bug 1 - losing hands get paid

  if outcome == "win":
      self._pay(BET * 2)
- elif outcome == "push":   # only a tie refunds the bet
+ else:                     # ...now EVERY non-win pays
      self._pay(BET)

Collapsing the elif push to a bare else means a lose outcome also emits a payout. Real money leaks on every loss. The monitor catches it squarely: the losing-hand-not-paid rule fired on eleven of the user's own honest losing hands.

Policy in play: 05 - a losing hand is never paid  ·  Trigger: stand and lose to the dealer  ·  Class: normal-use

Bug 2 - a tie is paid as a win

- if dealer_total > 21 or player_total >  dealer_total:
+ if dealer_total > 21 or player_total >= dealer_total:
      outcome = "win"

Loosening > to >= settles a push (equal totals) as a win and pays it double; the push branch is now dead. No policy forbids paying a win, so the monitor never flags it - a genuine money bug that is a pure coverage gap.

Policy in play: none - no rule asserts on pushes  ·  Trigger: stand with a total equal to the dealer's  ·  Class: subtle · slip-through

Detection

How the failure surfaced

The same defect through the framework's three independent channels, plus what the blind user actually noticed.

Channel A - live runtimecatch + miss

Rule 5 fired violated on eleven honest losing hands across a 55-hand session. The tie-paid-as-win bug produced no verdict - no rule watches for it.

Channel B - replay gatered · exit 1

replay_check.py failed (8 violations vs the pinned 6) as the healthy hands leaked payouts.

Channel C - stability contractrisk · exit 1

Six behavior-risks, all tracing to BlackjackTable.stand; the stability panel independently fingered the changed function.

The blind userfound 2 / 2

Played 55 hands. Caught the losing-payout bug via the monitor and the tie-payout bug by eye - noticing the table never once produced a "push" and paid ties double.

One money bug caught loudly, one just as costly slipping through. The monitor is superb at the property a rule asserts (losers must not be paid) and blind to the property no rule names (ties must refund, not double-pay). The lesson is not that RV failed - it is that coverage equals the rules you wrote.
