The implanted bugs

policy-targeted app/fleet.py

wipe() emits the lifecycle state "wipe" instead of "wiped" (dropped 'd', a wrong-status-string typo a developer could introduce during a refactor).

Expected effect: No device ever emits the state "wiped", so policy 03 ("every retired device was wiped before retirement", which does `When a device is "retired" Then a device is "wiped" before`) can never find a preceding wiped event. Every device that is wiped-then-retired now VIOLATES rule 03 instead of satisfying it (e.g. the healthy D-1 and D-WINDOW devices in the gate), raising the violation count above the pinned EXPECTED and flipping healthy flows to red.

blind-spot probe app/fleet.py

record_provision_check() emits the provision-check lifecycle event twice (a stray duplicate/double-processing emit dressed up as a late-subscriber re-record). The provision_ok / provision_failed event is now recorded twice per check.

Expected effect: The provisioning outcome is double-recorded. This is a real behavioral defect (duplicated events in the stream) but it lands in a monitor blind spot: provision_ok / provision_failed appear in the policies only as `previously`/`before` operands, never as a trigger (When/Given), so the duplicate creates no new verdict, and the event immediately preceding "activated" is still "provision_ok", so rule 01 stays satisfied. No policy counts events, so the duplication is invisible to all six rules and does not change the pinned verdict/violation counts.

Blind user (monitor only)

An agent that never saw the ground truth, working only from the monitor:

  • FleetService.wipe() emits the lifecycle state literal "wipe" instead of "wiped". The LIFECYCLE_TYPE contract comment and policy 03 (Then a device is "wiped" before) both expect "wiped". As a result every device following the HEALTHY wipe->retire path (D-1, D-WINDOW) is falsely reported as violating 'every retired device was wiped before retirement'. Surfaced by the replay gate (2 unexpected violated verdicts + exit-1 count mismatch 9 vs pinned 7), by the stability check (app behavior risk naming wipe on the device.lifecycle emit path), and confirmed in the raw trace. via both
  • record_provision_check() calls self._lifecycle(...) twice, so every provision_ok/provision_failed lifecycle event is emitted twice (visible in trace lines 2-3). The stability analyzer flags record_provision_check as a changed function on the device.lifecycle emit path (behavior-risk), i.e. a behavioral change from the committed catalog baseline. It causes no wrong verdict in this trace and an in-code comment rationalizes it, so this is lower-confidence, but worth a human glance. via both
