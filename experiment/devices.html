What it is

A device + sensor fleet tracker

A FleetService: devices go provisioned → provision-ok → activated → act → quarantined → wiped → retired; sensor feeds push readings under their own key. Five temporal forms are exercised across the six rules.

Retirement is the device terminal; rule 2's containment is armed from quarantine until retirement.

event model  · device.lifecycle and device.action keyed by device_id; terminal device.retired; sensor.reading keyed by sensor_id.

The monitored rules

What the user asked the monitor to enforce

Verbatim from the committed monitoring/policies/. These are the human's own words; the engine owns the verdict.

Feature: retirement safety Scenario: every retired device was wiped before retirement When a device is "retired" Then a device is "wiped" before
Feature: device activation ordering Scenario: activated only immediately after its provision check passed When a device is "activated" Then a device is "provision_ok" previously
Feature: quarantine containment Scenario: a quarantined device performs no non-blocked action Given a device is "quarantined" Then a device performs a non-blocked action never happens
Feature: sensor feed health Scenario: a sensor feed only ever reports ok readings Then a sensor reading is "ok" always holds

The sabotage

The bugs planted in the app code

Bug 1 - wipe records the wrong lifecycle state

  def wipe(self, device_id):
-     self._lifecycle(device_id, "wiped")
+     self._lifecycle(device_id, "wipe")

No device ever reaches the state wiped. The retirement-safety rule (a retired device was wiped before retirement) becomes unsatisfiable: it can no longer tell a safe wipe-then-retire from a dangerous retire-without-wipe, and fires on every retirement - including the demo's own device the build had called healthy.

Policy in play: 03 - retirement safety  ·  Trigger: wipe(D) → retire(D)  ·  Class: normal-use

Bug 2 - the terminal loses its timestamp offset

  def retire(self, device_id):
      self._lifecycle(device_id, "retired")
-     self._emit(retired_terminal, self._clock() + 1e-3)  # ordered after
+     self._emit(retired_terminal, self._clock())         # shares the timestamp

The tiny +1e-3 that ordered the terminal after the retired status is dropped, so both now share an event time. Equal timestamps fall back to canonical content ordering - a subtle ordering slip that no policy asserts on. The user did not notice it.

Policy in play: none binds the ordering - slipped through  ·  Trigger: every retire  ·  Class: subtle · slip-through

Detection

How the failure surfaced

The same defect through the framework's three independent channels, plus what the blind user actually noticed.

Channel A - live runtimecatch

The wiped-before-retire rule fired violated on the demo's own "healthy" device D-1 - an unmistakable live signal that something about wipe was wrong.

Channel B - replay gatered · exit 1

replay_check.py failed with a count mismatch (9 vs the pinned 7), the two extras being the healthy devices the wipe bug now trips.

Channel C - stability contractrisk · exit 1

The stability contract flagged the wipe and retire emit sites as behavior-risk.

The blind userfound 1 / 2

Caught the wipe bug through all three channels and confirmed the activation-predecessor rule still works. The timestamp-ordering bug was not noticed - the predicted slip-through.

A clean runtime catch, and a predicted miss. A wrong state string that makes a safety rule unsatisfiable is exactly what the monitor is for, and it fired on the app's own supposedly-healthy device. The bug that slipped - an ordering detail no rule asserts - was flagged as a slip-through before anyone played.
