What it is

A code-driven lending service

A LendingService class: a member borrows a book copy (starting a loan), may renew it, returns it, or reports it lost. Returning and reporting-lost both close the loan.

The service performs operations and emits an event at each transition; it does not itself enforce the temporal rules - the monitor is the runtime safety net.

event model  · one type loan.status keyed by loan_id, statuses borrowed / renewed / returned / lost. No terminal event - a lost loan stays watched so a later illegal renewal is still caught (reclaimed by a quiescence TTL).

The monitored rules

What the user asked the monitor to enforce

Verbatim from the committed monitoring/policies/. These are the human's own words; the engine owns the verdict.

Feature: a lost loan is never renewed Scenario: once a loan is reported lost it must never be renewed Given a loan is "lost" Then a loan is "renewed" never happens
Feature: a returned loan is never renewed Scenario: a returned loan is never renewed afterwards Given a loan is "returned" Then a loan is "renewed" never happens
Feature: a loan is returned only after it was borrowed Scenario: a loan can only be returned after it was borrowed When a loan is "returned" Then a loan is "borrowed" before
Feature: every borrowed loan is settled in time Scenario: settled within 21 seconds When a loan is "borrowed" Then a loan is returned, renewed, or reported lost within "21" seconds

The sabotage

The bugs planted in the app code

Bug 1 - report_lost emits the wrong status

  def report_lost(self, loan_id):
-     self._status(loan_id, LOST)      # emits "lost"
+     self._status(loan_id, RETURNED)  # emits "returned"

A wrong sibling constant. The lost event never fires. Now a borrow → lost → renew sequence trips the returned-never-renewed policy (05) - which is technically a violation, so the dashboard turns red and looks like it is working - while the policy the user actually wrote for this, lost-never-renewed (02), receives no lost event at all and sits as a permanently empty, satisfied-looking card. The alarm fires on the wrong door.

Policy in play: 02 (goes dormant) & 05 (fires by accident)  ·  Trigger: borrow(L) → report_lost(L) → renew(L)  ·  Class: normal-use

Bug 2 - borrow swaps two payload fields

  def borrow(self, loan_id, member_id, book_copy_id):
-     ...payload {"member_id": member_id, "book_copy_id": book_copy_id}
+     ...payload {"member_id": book_copy_id, "book_copy_id": member_id}

Pure data corruption in the event payload. No policy binds these fields, so the runtime monitor is completely blind to it - the only trace is in the raw event feed. This is the archetypal coverage gap: a monitor reads only the fields a rule references.

Policy in play: none - outside all policy coverage  ·  Trigger: every borrow  ·  Class: subtle · slip-through

Detection

How the failure surfaced

The same defect through the framework's three independent channels, plus what the blind user actually noticed.

Channel A - live runtimemisdirected + blind

The renew-after-lost fault turned policy 05 red instead of policy 02, and policy 02's card sat dormant and empty. The field-swap was invisible. The live cards were technically firing but pointing at the wrong rule - the user had to notice the dormant card to understand it.

Channel B - replay gatepass · exit 0

The pinned replay_check.py stayed green (5 violations, as pinned): the misdirected fault preserved the total count, so the numeric gate saw nothing wrong.

Channel C - stability contractrisk · exit 1

catalog diff --fail-on-app-risk failed, flagging behavior-risk on the borrow emit slice ("borrow changed; LOST constant changed") against all five policies. It named the changed code even though the runtime was fooled - but as a soft risk, not a hard break.

The blind userfound 2 / 2

Caught both by eye: spotted the dormant policy-02 card and traced the misdirected verdict, then read the raw payloads to find the field swap, and reported the stability strip as the corroborating signal.

The value and the limit in one demo. A monitored program's dashboard can look healthy or even correctly-red while the specific policy you care about is silently switched off. The stability contract flagged the code change; a careful operator connected the dots. Reading verdicts alone would have missed which rule went dark.
