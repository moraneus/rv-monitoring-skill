The implanted bugs

policy-targeted app/service.py

return_() double-emits: after the correct RETURNED status it also emits a stray RENEWED status (framed as 'releasing a renewal hold'). Every returned loan now produces a renewed event immediately after being returned.

Expected effect: Every healthy return (L-101, L-102, L-505 in the demo driver) is followed by a renewed event on the same loan_id. This directly violates policy 05 (returned_never_renewed: 'Given a loan is returned, then a loan is renewed never happens'), turning that card red for loans that returned cleanly. It also adds a spurious renewed event that policy 04 (renew_after_borrow) sees as fine (borrow precedes it), so no false positive there.

blind-spot probe app/service.py

report_lost() emits the wrong status constant RENEWED instead of LOST (adjacent-constant copy-paste error). A copy reported lost is recorded as a renewal.

Expected effect: report_lost(L-404) now emits status 'renewed' instead of 'lost'. Policy 02 (lost_never_renewed) scopes on 'Given a loan is lost', which now never fires for L-404, so the intended renew-after-lost violation goes UNDETECTED by policy 02 (the safety rule is silently defeated). The subsequent legitimate renew(L-404) just looks like a second renewal after a borrow, so it stays green everywhere. Net effect: a genuine safety violation (renewing a lost copy) is no longer caught, because the emitted event type is wrong -- the classic silent-telemetry-gap blind spot.

Blind user (monitor only)

An agent that never saw the ground truth, working only from the monitor:

  • return_() emits a phantom 'renewed' event after 'returned'. app/service.py return_() calls self._status(loan_id, RETURNED) then self._status(loan_id, RENEWED). A returned (closed) loan should never emit a renewal. Monitor surfaced it as (a) a red stability gate naming service.LendingService.return_ changed on the emit path, and (b) a real 'returned never renewed' violation on L-return-then-renew plus a spurious extra 'renewed only after borrowed' violation on L-return-first. via both
  • report_lost() emits 'renewed' instead of 'lost'. app/service.py report_lost() calls self._status(loan_id, RENEWED); it is documented to close the loan as lost and should emit LOST. Consequence: the 'lost' status is never emitted, the LOST constant is dead, and policy 02 'lost never renewed' can never fire - it stays pending even on the L-lost-then-renew seed that demo.py claims turns it red. Monitor surfaced it as a red stability gate flagging the service.LOST constant changed in the emit slice, and as the never-firing (silently pending) policy 02. via both

The replay_check.py verdict gate returns exit 0 because the pinned EXPECTED counts (45 verdicts, 5 violations) still match by coincidence: Bug B removes the intended rule-2 violation (L-lost-then-renew stays pending) while Bug A adds a compensating extra violation on L-return-first. So a user glancing only at the replay exit code would be fooled; the catalog-diff stability gate (exit 1) is the check that unambiguously fails. The stability gate flags both defects precisely (return_ function change + LOST constant emit-slice change). Only return_ and report_lost are buggy; borrow() and renew() are clean.
